# Migration to 0.2.0

Release 0.2.0 changes how claims are classified and written, and its checker enforces the new statement form. Claim documents written for 0.1.x fail the 0.2.0 checker until they are migrated.

## Changes

- **Meaning:** Every claim, including its title and the introduction definitions it uses, states meaning in plain language and refers to no implementation mechanics, such as a backtick, a function call, a return, a value in code, or a data structure, as defined in [Claims specify meaning](../SKILL.md#claims-specify-meaning).
- **Warrant:** A claim is warranted when its characteristic is intentional, meaningful, and provable, as defined in [Choosing when and how to write Semantic Claims](../SKILL.md#choosing-when-and-how-to-write-semantic-claims). A characteristic that exists solely for implementation purposes warrants no claim.
- **Kind:** A claim's kind follows its meaning, as defined in [Claim kinds](../SKILL.md#claim-kinds). A response that is always true, or true for as long as a present state lasts, such as what the system shows while a filter is applied, is an invariant, even when an event, such as applying the filter, starts that state. A response that the system performs once for each occurrence of an event, such as a request, the system's creation, a failure, or a notification the system sends, is a scenario with that event as its trigger.
- **Statement form:** Every statement is one sentence in an EARS pattern of its kind, with its EARS keywords in uppercase, as defined in [Claim kinds](../SKILL.md#claim-kinds).
- **Statement rules:** Every statement has one `SHALL` and one response, uses `where`, `while`, `when`, `if`, `then`, and `shall` as uppercase keywords exclusively, states its response positively, states a set with "exactly" or "each" in place of "only", and puts each condition on a trigger's input in the trigger, as defined in [Claim kinds](../SKILL.md#claim-kinds).
- **Introduction:** The introduction defines terminology used in claims, contains no statement that belongs in a claim, and defines each term a claim uses with a meaning specific to the system, as defined in [Document structure](../SKILL.md#document-structure).
- **System name:** In every statement, the system's name before `SHALL` equals the claim document's `#` heading, as defined in [Claim kinds](../SKILL.md#claim-kinds).
- **System:** Every event into or out of a system belongs to its interface, so a claim stored as cross-cutting can belong to a local system; see [Cross-cutting claims](../SKILL.md#cross-cutting-claims).
- **Checker:** The checker rejects a claim document that contains a backtick, an empty statement, a statement that does not follow the EARS template with uppercase keywords, a statement that contains `where`, `while`, `when`, `whenever`, `if`, `then`, or `shall` outside an uppercase keyword or its system name, a statement that contains `only`, a statement whose pattern does not match its document's kind, and a statement that does not name its system as the document's `#` heading does.

## Procedure

For each claim document in the project:

1. Split each statement that states more than one rule, or more than one response that a test can verify separately, into one claim for each, each with its own proof tests.
2. Rewrite each statement, title, and introduction definition that refers to implementation mechanics to state the meaning they represent, in plain language, as in "WHILE open" in place of "WHILE `isOpen()` returns true". For each claim whose characteristic exists solely for implementation purposes, propose to the user deleting the claim and its proof tests.
3. Decide each claim's kind by its meaning with [Claim kinds](../SKILL.md#claim-kinds), and read the system's interface to decide its system with [Definitions](../SKILL.md#definitions) and [Cross-cutting claims](../SKILL.md#cross-cutting-claims).
4. Move each claim whose kind or system differs from its document's to the document of its system and kind, creating that document and its proof file if they do not exist. Move the claim's proof tests with it, and copy the introduction definitions the claim uses. If the claim's system changed, rewrite its proof tests to use only the new system's interface. Give the claim an identifier that is unique in its new document, and update every proof and reference that uses the old identifier. Delete a document and its proof file after every claim in it has moved.
5. Rewrite each statement as one EARS sentence of its kind, with its EARS keywords in uppercase and the same meaning. Move definitions to the document's introduction. State earlier events in the trigger or relative to it, never in a `WHILE` clause. Put each condition on a trigger's input in the trigger. Give each statement one `SHALL` and one response. Move each condition written with a lowercase `where`, `while`, `when`, `if`, or `then` into a clause, into a term the introduction defines, or into a separate claim. State each response as what the system does, and replace "only" with "exactly" or "each". Move each introduction sentence that belongs in a claim into a claim. Define in the introduction each term a claim uses with a meaning specific to the system, including a term that another claim document defines. Write the text of the document's `#` heading as the system's name before `SHALL`, adding the heading if the document has none. Removing a kind word, such as "Invariants", from a heading keeps the system's name; propose every other new name to the user. Retitle each claim whose title the new statement does not imply, and change its proof titles to match.
6. Review each document with the [review checks](../SKILL.md#review-checks), and fix each finding. Check each pair of claims, in this document and in the documents of systems it interacts with, whose conditions are both true in one state: that state satisfies both responses. Merge claims that state cases of one rule.
7. Run the checker and the proofs.

Keep each claim's full meaning: the behavior its statement states and the behavior its proof asserts. Add a proof test for each part of a statement that no proof asserts. If the statement and its proof differ, a rewrite requires a choice between meanings, or a claim's kind depends on a behavior whose intent is undecided, ask the user before changing the claim.

Report the claims moved, split, rewritten, and proposed for deletion, and the questions asked.

## Examples

- Invariant, rewritten: "Focus stays inside the modal while it is open." becomes "WHILE open, the modal SHALL contain the focused element."
- Invariant moved to the scenario document, with its call rewritten as meaning: "`lookup(word)` returns the definition of each word in the dictionary." becomes "WHEN a word that the dictionary contains is looked up, the dictionary SHALL respond with the word's definition."
- Scenario, rewritten and split: "**Given** a payment request has been accepted, **When** the client submits the same request identity, **Then** the response contains the outcome of the accepted request, and the number of charges is unchanged." becomes two claims, "WHEN a client resubmits a payment that the payment service accepted earlier, the payment service SHALL respond with the outcome of the earlier accepted payment." and "WHEN a client resubmits a payment that the payment service accepted earlier, the payment service SHALL leave the number of charges unchanged."
- Invariant moved to the scenario document, with its call rewritten as meaning: "A rejected submission leaves `accepted()` unchanged." becomes "IF a submission is rejected, THEN the form SHALL leave the form's accepted submission unchanged."
- Invariant moved to the scenario document, with its return, condition, and negation rewritten: "An entry is never returned when its time to live has passed." becomes "WHEN an entry whose age is at least the entry's time to live is looked up, the cache SHALL report a miss.", with the introduction "An entry's *age* is the time since the entry was stored."
